Deployment

Deploy a validated, versioned GHCR image behind a reverse proxy while keeping production and demo identities isolated.

Release image pipeline

Every pull request runs tests, static analysis, dependency checks, Compose validation, a Docker build, and a live health check. Successful pushes to main publish:

  • ghcr.io/paulkakell/timeboardapp:00.13.00 — version tag used by Compose
  • ghcr.io/paulkakell/timeboardapp:sha-<commit> — commit-oriented audit and rollback tag
  • ghcr.io/paulkakell/timeboardapp:latest — latest successful main build

The image is published for linux/amd64 and linux/arm64 with OCI metadata, provenance, and an SBOM.

Package visibility
If the GHCR package is private, authenticate the deployment host with a package-read token. For unauthenticated pulls, change the package visibility to public in GitHub.

Recommended production shape

Image

Version pin

Set TIMEBOARDAPP_TAG to a release or SHA tag instead of relying on an untracked local build.

Storage

Dedicated /data

Give every stack its own host directory for settings.yml, the SQLite database, logs, and backups.

Network

Unique alias

Set a unique CONTAINER_NAME. Compose registers that value as the reverse-proxy-facing network alias.

Production and demo configuration

Production:

TIMEBOARDAPP_IMAGE=ghcr.io/paulkakell/timeboardapp
TIMEBOARDAPP_TAG=00.13.00
PORT=3010
CONFIG_DATA=/srv/timeboardapp/production
CONTAINER_NAME=timeboardapp
INTERNAL_NETWORK=net_internal
EXTERNAL_NETWORK=net_external

Demo:

TIMEBOARDAPP_IMAGE=ghcr.io/paulkakell/timeboardapp
TIMEBOARDAPP_TAG=00.13.00
PORT=3011
CONFIG_DATA=/srv/timeboardapp/demo
CONTAINER_NAME=timeboardapp-demo
INTERNAL_NETWORK=net_internal
EXTERNAL_NETWORK=net_external

Each data directory must contain its own settings.yml. Production should use demo.enabled: false; the public demo should use demo.enabled: true.

Reverse proxy routing

When Nginx Proxy Manager shares the external Docker network, use the unique alias and container port:

timeboard.bitterhost.com  -> timeboardapp:8888
demo.timeboardapp.com     -> timeboardapp-demo:8888
Do not use the Compose service alias
The service is named app in every stack. That name is intentionally not a proxy target because it is duplicated when multiple stacks share a network.

If the proxy reaches the Docker host instead of the shared Docker network, forward to host ports 3010 and 3011.

A reverse proxy should forward Host, X-Forwarded-Proto, and X-Forwarded-For, and allow long-lived Server-Sent Event connections for browser notifications.

Base URL

Set the public URL independently in each stack:

app:
  base_url: "https://timeboard.bitterhost.com"

The demo stack should use https://demo.timeboardapp.com. The value may also be supplied through TIMEBOARDAPP_BASE_URL.

First migration to 00.13.00

This release changes the Compose service name to app and removes the local build: . path. Back up the data directory, then remove the previous service before starting the GHCR-backed service with the same configured container name:

docker compose down --remove-orphans
docker compose pull
docker compose up -d
docker compose logs -f app

The bind-mounted /data directory is retained. No database migration or data conversion is introduced by this release.

Upgrades

  1. Back up the database and settings directory
  2. Set TIMEBOARDAPP_TAG to the target release
  3. Run docker compose pull
  4. Run docker compose up -d
  5. Review logs, /healthz, the UI, API, and Admin → Validation

Rollback

Pin TIMEBOARDAPP_TAG to a previously published release or exact sha-<commit> tag, then pull and recreate the service:

docker compose pull
docker compose up -d

For the initial migration from a locally built pre-00.13.00 image, retain or retag the old local image until the new deployment is validated. Version 00.13.00 has no database schema changes, so a database rollback is not required.

Backups

Back up the complete host directory mapped to /data. The Admin UI also supports JSON export/import and scheduled backup retention.
