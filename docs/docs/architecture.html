Docs · Architecture

Architecture

FastAPI and SQLite at runtime, with a validated GitHub Actions pipeline that publishes versioned multi-architecture containers to GHCR.

Runtime components

Backend

FastAPI

Serves Jinja-rendered pages and a JSON API. UI authentication uses signed sessions; API authentication uses JWT bearer tokens.

Storage

SQLite + SQLAlchemy

Application data, metadata, and runtime settings are stored in a single persistent volume mounted at /data.

Jobs

Background scheduler

Runs overdue notification scans, purges, backups, reminder delivery, logging retention, and optional demo resets.

Container release flow

Pull request / main push

pytest + compileall + Bandit + pip check + pip-audit
        |
        v
docker compose config + Docker build + /healthz smoke test
        |
        v
Buildx multi-architecture build (amd64 + arm64)
        |
        v
ghcr.io/paulkakell/timeboardapp
  - release version tag
  - sha-<commit> tag
  - latest tag
  - OCI labels + provenance + SBOM

The publish job runs only after validation succeeds. It uses the repository-scoped GitHub token with package-write permission; validation jobs receive only repository-read permission.

Multi-instance networking

Each Compose stack uses the fixed service name app, but registers its unique CONTAINER_NAME value as the proxy-facing network alias.

Shared proxy network
  Nginx Proxy Manager
      |-- timeboardapp:8888      -> production /data
      `-- timeboardapp-demo:8888 -> demo /data

The duplicate service alias app is never used as a reverse-proxy target. Production and demo also use distinct host ports, settings files, databases, and public base URLs.

Task recurrence model

TimeboardApp supports multiple recurrence styles:

  • Post-completion interval — schedule from the actual completion time
  • Multi-slot daily — choose the next configured clock time
  • Fixed clock interval — retain an anchored schedule independent of completion time
  • Nested recurring task trees — recreate child work when the parent recurs

Notifications

Notifications are configurable per user and may be delivered through browser SSE, email, WNS, Gotify, ntfy, Discord, generic webhooks, and generic APIs. Dispatch status and errors are retained in notification-event records.
